## Design notes for `src/morphlex.ts`

### `morphlex-dirty` attribute

The `flagDirtyInputs` function sets a `morphlex-dirty` attribute on form elements where the user has modified the value (i.e., the DOM property has diverged from the content attribute). This attribute is not read for any conditional logic — its purpose is to act as a sentinel that forces `isEqualNode` to return `false` for dirty inputs. Without it, `#morphOneToOne` would short-circuit on line `if (from.isEqualNode(to)) return` and skip syncing DOM properties like `.value`, `.checked`, and `.selected`. The attribute is cleaned up at the start of `#visitAttributes`.

A dirty element, or one holding a dirty element, can't equal its target, so it's left out of the `isEqualNode` pass, and siblings are then matched while ignoring the attribute. Those are bucketed by their shape (the whole subtree's names, attributes apart from `morphlex-dirty`, and text, including template content), so many changed siblings aren't compared pair by pair, and a target takes the first free element in its bucket. A target holding a `morphlex-clobber` element is left out of this pass, since it can't keep the user's changes. Otherwise a changed control would be paired with whatever comes first, and inserting an item before the user's pick would move the pick to the new item. With `preserveChanges`, a changed checkbox, radio or option holds the user's choice of its value (and name). So before matching by name, it's matched to a target with the same choice, and a wrapper without its own identity (like a `label`) that holds such controls is matched to a target holding the same choices. A select holding changed options is matched the same way, even though it has a name. Within each step, targets holding all the choices the user picked come first (holding the fewest choices first), then targets holding all the choices including options and radios they deselected or moved away from, then targets holding any choice they picked, then any choice. Wrappers holding more choices pick first. A control inside a `morphlex-clobber` element of the target, or one itself, doesn't count as holding a choice. Targets without their own identity come first, so a new label with an id can't take an old label's place, though a label that gains an id still keeps its controls. A changed control, or a select, likewise tries targets without an id first. Within those, targets with the same attributes apart from `class` and `style` come first, so a form doesn't take another form's target just because both hold the same checkbox, and then targets holding all of the wrapper's choices (counting duplicates), preferring the one holding the fewest. Each step pairs as many wrappers with targets as it can (a bipartite matching), so one wrapper taking a target never leaves another without one it could have had. Each wrapper first takes the first free target holding one of its choices (targets are indexed by choice, and by attributes in the steps needing the same attributes), and paths are only searched for the rest, breadth first and without recursion, through the indexed targets only, reaching each target once. Until a search succeeds, the targets a failed search reached are skipped, and a wrapper alike to one whose search failed isn't searched, so many identical wrappers stay fast. A wrapper only takes a target with the same `is`. An option is keyed by the nearest select around it up to the morph's root. A target's option in a morph rooted inside a select, with no select of its own below the root, takes the enclosing select's name, even when the target is still in another select, and a morph rooted at a select, or inside a select matched to a live one, gives the target's options the live select's name, so a vetoed rename keeps them matched. An option in a datalist holds no choice. A control's choice includes its `is` and its `form` attribute (unless it names the form the control is in, which for a target's control outside any form in the target is the form around the morph, since that's where it ends up), and an option's includes its select's name (an absent name counts as empty), `form` and whether it's a drop-down, a list box or multiple. A control that has, or sits inside an element below the wrapper that has, an id pairing a live element with a target it can be morphed into moves with that element, so it holds no choice, in the live tree or the target. A wrapper's choice also includes the namespaces, names and `is` of the elements between it and the control, since the wrapper's morph only keeps a control along a matching path. The morph keeps the flagged controls in a set rather than reading the attribute, since a nested morph from a callback can clear it. A nested morph puts back the flags of the morphs running around it that it cleared, so the outer morph never finds a control the user changed equal to its target, wherever the nested morph moved it. A changed control is never soft-matched to a target with another choice, unless the target has `morphlex-clobber`. When an element holding the user's changes is still without a target after the choice steps, in both modes, it takes a target with the same shape that an untouched sibling took, so the untouched sibling goes instead, or takes another target it equals. This runs after the choice steps, so it never takes a target they gave another element, and it skips targets holding a `morphlex-clobber` element.

An input counts as dirty only when the browser says the user changed its value. The browser sanitizes `.value` for many types (a range with no value reads "50", email trims spaces, number drops invalid text), so `.value` differing from `defaultValue` isn't enough. `hasDirtyValue` reads the browser's dirty value flag through a clone in an inert document, which keeps the flag without upgrading a customized built-in. `#resetFormProperties` compares with the target's own `.value`, since the browser sanitizes both, and leaves an untouched input alone when its `min`, `max`, `step` or `multiple` update was vetoed (a value the user typed is still reset). An untouched range can still differ, because the browser clamps it as `min` and `max` change. Then setting its `value` attribute again sanitizes it afresh without setting the flag, which `resanitizeValue` tries on a clone first. Only when that doesn't help does it assign `.value`, which sets the flag. A textarea compares against its default with carriage returns turned into line feeds, as the browser does.

An option counts as dirty when its `.selected` differs from what the browser would select from the markup alone. A drop-down with no `selected` attribute shows its first enabled option as selected, so comparing against `defaultSelected` would flag every untouched select and get unnamed ones replaced.

The browser keeps a select's selection when options are added, moved, or when the select switches between a drop-down, a list box and a multiple select. So without `preserveChanges`, after visiting a select's children, `#syncDefaultSelection` selects what the markup selects, unless that would change an option whose `selected` update was vetoed or that sits in a subtree whose visit was vetoed. A drop-down's vetoed option can still be selected again, since an earlier option gaining `selected` takes the selection from it. It runs again for the same selects when the morph settles, because option wrappers can still move or be removed after the select's children were visited. With `preserveChanges` it never changes the selection, because a user who picks the default option again looks untouched, so the browser's own record of the choice decides (Joel's call). The exception is a select without a selection (an untouched list box, or a multiple select the user deselected) that becomes a drop-down: the browser picks its first option wherever the morph has got to with the options, which is neither the user's choice nor the markup's, so it selects what the markup selects. A morph rooted inside a select never visits the select, so `morph` and `morphInner` sync the enclosing select when the morph settles, before the root's after callbacks, but only when the morph changed which options the markup selects or which options the select shows (updating an option's `selected` or `disabled` attribute can change what it shows while the markup selects the same options), or when it reset an option's selection, since WebKit can keep showing an option that's deselected when the first option it would show is in an optgroup. So a vetoed morph changes nothing.

The parser selects the first option of a drop-down with no `selected` option, so a new option from the target can arrive selected and take the selection when inserted. `clearImplicitSelection` clears that on every insertion into a select (including one-to-many morphs and wrappers in customizable selects), once the node has left the parsed select. It leaves options with a `selected` attribute alone, since the browser would select those anyway, and options of a select inside the new node, and live nodes passed as the target.

The browser copies the selected option's content into each `selectedcontent` of a drop-down (a customizable select), so the morph leaves its children alone: the target's copy shows what the target's markup selects rather than what the user picked, and WebKit leaves it empty when parsing a template. The browser only copies the option when the selection changes or the `selectedcontent` is inserted, so changing the selected option's content leaves the old copy. So when the morph settles, `refreshSelectedContent` inserts each `selectedcontent` that doesn't match the selected option again, in the selects the morph visited and the select around the root, for the browser to copy the option afresh. Browsers without customizable selects morph it like other markup.

### Focused contenteditable

With `preserveChanges`, the focused editing host (the `isContentEditable` element that's active in its document or shadow root when the morph starts, so a target that adds or removes `contenteditable` doesn't change it) keeps its children as the user left them, like a typed-in input keeps its value. So does an element inside it that's the morph's root. Its attributes are still updated, and nothing inside it moves elsewhere, as when `beforeChildrenVisited` vetoes. When its target holds a `morphlex-clobber` element, its children are visited after all: the clobbered element follows the markup, and so do the editor's own children (its text and which elements it holds), while the other elements in it keep their content. Keeping only the clobbered branch would need a partial child pass, which isn't worth its code for this case. Whether the user typed in it can't be told, so being focused stands in for that. Without focus, or without `preserveChanges`, it follows the markup.

### Content attributes vs DOM properties for form elements

`#visitAttributes` only updates content attributes (`setAttribute`/`removeAttribute`). It never assigns `.value`, `.checked` or `.selected` itself, so a `beforeAttributeUpdated` veto leaves both the attribute and the property alone. Attribute updates are safe under `preserveChanges`: once the user has changed a control, `setAttribute("checked", "")` only changes `defaultChecked`, not `.checked`, and the same goes for `selected` and `value`, because the property decouples from the attribute per the HTML spec.

### Resetting user changes when not preserving

When `preserveChanges` is false, `#resetFormProperties` runs after the attribute passes and sets each property to what the target markup says, including edits where neither side has the attribute. It skips a property when its attribute still differs from the target, because that means `beforeAttributeUpdated` vetoed the update. It never assigns `.value` on checkbox, radio or file inputs.

Moves complete out of document order, and a radio that moves can join another radio group, so resetting radios one at a time can leave a group showing the wrong radio. Adding `checked` to a radio unchecks the rest of its group too, even radios later in the document, and a node list morph adds its first node after the others. So when a reset changes a radio's `.checked`, the target checks a visited radio, a radio moves, or a node list morph adds radios, its group is synced when the morph settles: each radio's `.checked` is set from its `checked` attribute in document order, so the last one the markup checks wins, as when parsing. Radios outside the morph are left alone, and so is a whole group with a radio in a vetoed subtree or with a vetoed `checked` update, since checking one radio unchecks the rest. Nothing is synced under `preserveChanges`.

A move can also change radio groups outside the morph: a checked radio that joins a group unchecks the rest of it, and moving a form briefly takes the radios outside it that use its `form` attribute out of its group. Adding or removing a form with an id, or changing a form's id or a radio's `form` attribute, changes which form such radios belong to too (and changing a checked radio's name, or turning a checked input into a radio, is handled the same way), and Firefox and Safari briefly put a radio that changes form in the group of radios without a form, where a checked one unchecks a radio it never joins. Chromium and Firefox also briefly reset the form of a radio with a `form` attribute while a form around it moves or is removed, so a checked one can uncheck a radio in another group for that moment. So these changes first uncheck the checked radios outside the changing node whose `form` attribute names a form id it holds (or the radio itself, or the checked radios inside a moving element that change form, or the checked radios with a `form` attribute inside a moving or removed node that holds a form, which are checked again straight after in both modes), and check them again straight after, in both modes, except that without `preserveChanges` the morph's own radios (or, inside a `morphlex-clobber` element, that element's radios) wait until it settles, so a radio the markup unchecks never unchecks the rest of its new group. A radio the morph checks again when it settles joins its group's radio sync, so a later radio the markup checks there still wins. A radio that's checked again straight after and still follows its `checked` attribute is unchecked by removing the attribute and checked by adding it back, because setting `.checked` would stop it following the markup. A radio outside the morph that joins a group with a checked radio inside the morph leaves that one checked, as when the page is parsed with the markup's radio later. When the morph settles, the radios that such a recheck unchecked (or that a checked radio inside the morph took the group from, including one the morph checks by adding its `checked` attribute or resetting `.checked`, and a new radio with a `form` attribute, which is inserted unchecked and checked straight after) are checked again if the radio that unchecked them has left their group (removed, or moved to another form or name) or is no longer checked, unless another radio in their group is checked or the markup decides their own `checked` (it removed the attribute, or the default reset visited them), so removing a form before a radio that names it, or changing a form's id before the radio's `form` attribute, doesn't lose a radio it only passed by. A live target also unchecks the radios where it is (in its own document or shadow root, and inside it) that name its forms, before anything takes it or its forms out of where they are, and checks them again straight after it's inserted. Without `preserveChanges` it also unchecks the checked radios inside it whose form changes, and checks them again when the morph settles if the markup or a veto keeps them checked.

### `open` on `details` and `dialog`

For these elements the `open` attribute is the live state the user toggles, and there's no default to compare it against. So with `preserveChanges`, `#visitAttributes` never adds or removes `open` on them. Without it, removing `open` from a dialog calls `close()` instead of `removeAttribute`, because removing the attribute leaves a modal dialog stuck in the top layer.

With `preserveChanges`, `flagDirtyInputs` flags every `details` (or every `dialog`), open or closed, when some are open and others closed in the live tree or the target, since whether the user toggled one can't be told. When they're all open or all closed, matching one to any other keeps what it shows, so none is flagged. So like a changed control it's left out of the `isEqualNode` pass, and its shape leaves out `open`, so an item keeps its own target among items that only differ by their open state, rather than an identical untouched sibling taking it. A row that differs from another only by its open state is just as likely to be the one the user toggled, so when one of the two goes, the passes' order decides.

Opening a `details` closes the other open one with the same `name` in its tree, and inserting an open one, or giving an open one that name, closes it instead. So a morph can leave the wrong item open, or none, before it settles: a new open item can arrive while the old one waits for a deferred removal, and the target can set `open` before `name`. Each item the morph means to be open is noted with its `open` value: an open item it inserts, and an item it visits, with the target's `open` unless the update was vetoed or `preserveChanges` keeps it as it was. When the morph settles, the noted items that ended up closed are opened again in document order, so the first one wins as when parsing, but only while nothing else in their group is open, because that one is wanted open too, outside the morph, vetoed or kept open by the user. WebKit's parser keeps every open item of a group (Chromium's closes all but the first, as a document does), so `closeLaterOpenDetails` closes the later ones in the target before the morph starts. Opening an item would close another that the morph may not have reached yet, so `#openDetailsItem` opens it outside its group by setting its name to "" for a moment, and rejoining the group closes it instead, to be opened again when the morph settles.

### Moving elements across parents

An element whose id appears exactly once in the live tree and once in the target is moved to wherever the target puts that id, even under a different parent, and then morphed into the target. This keeps typed text, focus and listeners. It applies even when the old parent's id changed and the parent itself is replaced. Options and optgroups never move, because an option's selection belongs to its select. An element whose `is` differs from its target's is recreated rather than moved or morphed, even when matched by id, because a customized built-in's definition is fixed when it's created. An element holding options (in a customizable select) only moves within its select (including into a new element inside it), and is only claimed there, since claiming takes the target out of its parsed select and changes which option that select picks. The morph root never moves. A root that can be morphed in place stays and takes its target's id, even when an element inside it has that id; a root that has to be replaced can be replaced by such an element.

An unmatched movable element isn't removed straight away. It stays where it is until the morph settles, and is removed then only if nothing took it. A removed node that still holds a movable element is also removed when the morph settles, after the element has had the chance to move out. The morph settles when the root's children have been visited or vetoed, before the root's `afterChildrenVisited`, before the root's `afterNodeVisited` when it has no children to visit, or when the root's replacement is done or vetoed, so the root's callbacks see the finished DOM. A one-to-many morph adds the extra nodes before morphing the first one, so they can take elements first.

The root's id counts towards uniqueness, but the root never moves. `morphInner` ignores the target's own element, so its id doesn't count. When matching siblings, a target whose live element can be claimed is left for the claim, so another live element never takes its id. When `beforeNodeVisited` or `beforeChildrenVisited` vetoes a visit, nothing inside that subtree moves elsewhere. A new node is searched for targets of movable elements just before it's inserted, so discarded targets never connect. A target claims its live element and leaves an empty comment as a placeholder. The move completes when the morph settles, because a later `beforeNodeVisited` or `beforeChildrenVisited` veto can still pin the element where it is. If it does, the target is added as a new node instead. A claimed element inside another claimed element waits until that one has moved, since its morph can still pin it: completing the inner move completes the outer one first. Likewise, an element inside a live element that a pending move's target holds waits for that move, and then for the move that claims the live element, so the live element's veto is asked before anything moves out of it. When moves would wait on each other in a cycle, the move that finds the cycle adds its target as a new node instead, and its live element stays where it is. An element never moves out of a movable ancestor that the target puts inside it, when that ancestor can be morphed into its target. That ancestor is only visited once the morph reaches it inside the element, too late for its veto to keep the element. So the element is recreated from the target instead, and the ancestor moves into the new one (Joel's call). Only the root's after callbacks are promised the final DOM (Joel's call). Callbacks for other nodes, including `afterNodeAdded`, can still see a placeholder where a moving element will go, or an element that is about to move out. A placeholder that a custom element's `connectedCallback` removed drops the move. `preserveChanges` is recorded when the target claims the element, so it's off when the target or one of its ancestors has `morphlex-clobber`.

### Focus and selection across moves

Safari has no `moveBefore`, so moving the focused element loses focus, Chromium's `moveBefore` resets a text control's selection, and no browser keeps the document's selection inside a moved node. The focused element is followed into open shadow roots through `activeElement`, and a shadow root's host holds what's inside it. An active body counts only when it's editable, as the editing host of the caret. When the morph starts, it notes the nodes holding the focused element inside the root, or the document's selection inside it. When placing children without `moveBefore`, `#pinFocused` keeps only the matches in order with the child holding one of those, so the longest increasing subsequence includes it and its siblings move around it, even when that moves more of them. With `moveBefore`, which keeps focus, the fewest nodes move, since moving siblings loses state that can't be put back, like their scroll positions (Joel's call). A move can still take them, such as one to another parent, or the insertion of a live target holding them. So just before each move (placing a child, completing a move, inserting a live target, before its claimed descendants leave it), `focusHeldBy` looks at where focus is at that moment, since a callback can move or refocus it, and saves the focused element and its selection (a text control's selection, or else the document's selection inside it) when the moved node holds the element or an end of that selection. Straight after the move, the element is focused again if it lost focus and no other element took it during the move (such as from a custom element's lifecycle callback or a focus handler, which a `focusin` on another element shows, in the element's document or the one it moves into, from the move until focus is put back, the body included), through the platform's `focus` rather than one the element defines, and its selection is put back if it changed, unless it no longer fits because a custom element's lifecycle callback changed the control or the text during the move, or an end of it has left the focused element. A caret that moved out of a focused contenteditable stays where the browser put it, inside the editor, because putting it back would leave it where typing goes nowhere. Before putting a selection back, the element's styles are brought up to date, because Chromium can drop a selection set in a node `moveBefore` just moved, and crashes when that node moved into a `details`. Doing this at each move, not when the morph settles, leaves anything a later callback does with focus or the caret alone, and lets the morph's own value changes move the caret as they would in place. When the element can't be focused where it is, such as in a closed `details` the morph opens later, it's tried again when the morph settles, with its selection followed by live ranges in the meantime, so a removal leaves its end where the removed node was (a move without `moveBefore` is a removal too, so an end whose node is still inside the element goes back to it), unless another element took focus instead (a focus handler can send it elsewhere) or a `focusin` showed one taking focus in the meantime, the body included.

A live target that's in the page is inserted with `moveBefore` too (when it's in the same document as the morph), so it keeps its state, such as a modal dialog staying modal or a popover staying open. Without `moveBefore` (Safari), any move takes modal dialogs and open popovers out of the top layer: a dialog stays open but stops being modal, and a popover closes. Morphlex doesn't put them back, since that took a lot of code for Safari alone (Joel's call, issue #122).

### Identical siblings

The `isEqualNode` pass gives each target the first free equal element, so when an element changes and a sibling is identical to its old version, the unchanged target takes the changed element's live node and the two would swap places. Identical live elements are interchangeable, so once every sibling is matched, each set of them is given to its targets in order, when that leaves more nodes in place than the order the passes chose (checked once for all the sets, so many sets stay fast). On a tie the passes' order stays, since moving other nodes instead changes which whitespace is reused. An element holding the user's changes is never identical to anything, but the `isEqualNode` pass gives its identical untouched sibling the target in its place, and the changed element takes a later one. So before that, in both modes, each changed element is ordered the same way with the untouched siblings of its shape, whatever targets they took, among targets with the same outline (the shape without attributes other than `is`, or a textarea's text, which is only its default value) and the same choices, counting duplicates, and for targets holding choices, the same attributes apart from `class` and `style`, as the choice pass prefers. Sets without a changed element are left to the ordering above. The kind pass can give an element a target with another outline, and the choice pass can give a changed control a target holding another value than its identical sibling's, so a changed element never trades into either. The shape, name and kind passes can cross changed elements, like inputs holding typed text, so they take their targets in order with the rest. Matching by name, in the name pass and the outline pass, skips an element that would be replaced rather than morphed, like an input of another type, so a same-name input of the target's type keeps its target and the user's text. The name pass still gives the target such an element once no target can take it to morph, because replacing it asks both vetoes before changing anything, while removing it and adding the target doesn't. This order always wins, even when it leaves fewer nodes in place, since the user's text belongs in its own row, whatever other nodes move (Joel's rule that user intent wins). Before the name and kind passes, when a changed element is still without a target, or an untouched sibling gave one its target, the free elements with the same outline as one take the targets with that outline in order, changed elements first, among the targets those passes would give them, so a typed row isn't given the first target of its tag when that has another outline, and an untouched row goes rather than a typed one when there are fewer targets. A target holding a `morphlex-clobber` element only takes an untouched element in that pass, so an earlier clobbered row doesn't shift the typed rows after it. When ordering, a changed element never trades into a target holding a `morphlex-clobber` element: such a target takes the first untouched sibling, and the other targets take the first free sibling while enough untouched ones are left for those. The equal target a changed element takes is morphed, not skipped. Untouched siblings of the same shape that no target took can stay instead of the ones the passes kept, since removing either leaves the same markup, so the ones that stay are chosen (a dynamic program over the siblings in order) to cross the fewest other matches, where crossing a changed element outweighs crossing all the others, and two changed elements crossing outweighs both, so typed rows of different kinds keep their order. On a tie, or when the program would be too big (a morph removing many of many identical siblings), the passes' choice stays.

### Addresses: `href` and `src`

A non-empty `href` or `src` pairs elements sharing it first, but doesn't stop an element matching by its tag, so a link, image or iframe whose address changes is morphed in place: a focused link keeps focus, and Chromium and WebKit keep a stylesheet applied until its new `href` loads. A `name`, an `id` and form controls still block matching by tag. A script with a `src` (or an SVG script with an `href`) is still replaced, because a script doesn't run again when its address changes. An address loads as soon as it changes, with the attributes the element has then, so `#visitAttributes` updates `src`, `href` and `srcdoc` after every other attribute is added, changed or removed, so an iframe's new page gets its `sandbox` and a link's new sheet its `integrity`.

### Whitespace between elements

Whitespace text nodes are only ever matched with whitespace. The live whitespace stays in place while the children are placed, and target whitespace reuses the live whitespace at the insertion point, so unchanged whitespace isn't removed and added again. Whitespace nothing reused is removed afterwards.

### Nodes whose removal was vetoed

A node whose removal `beforeNodeRemoved` vetoed stays where it is, and the nodes the morph adds or moves go after it, as other morphers place them (a b morphed into c with the removals vetoed gives a b c). So when placing children, the insertion point skips the kept nodes in front of it, with the matches still to move and the whitespace among them, up to the next node that stays put. A movable element waiting for the morph to settle counts as kept, since its removal can still be vetoed then. The whitespace before a vetoed node stays with it, but target whitespace still reuses the live whitespace where it is.

### Parsing string targets

`morph` and `morphInner` parse a string where `from` is, as `innerHTML` on its parent would. An `html`, `head` or `body` root takes the matching element of a parsed document, since a template drops those tags. Inside an HTML element whose innerHTML is text (a `script`, `style`, `textarea`, `title`, `noscript` and the like), the string is parsed in a new element of that name in the page's document, so tags stay text, a script's character references stay as written, and a `noscript` holds text as with scripting enabled. Inside SVG or MathML, the string is parsed in a shallow copy of the parent (an `svg` or `math` for a root without a parent) in the template's inert document, so nothing loads. So a `circle` stays SVG, and a `foreignObject`'s content, or an `annotation-xml`'s with an HTML `encoding`, stays HTML. Anything else is parsed in a template, which keeps table rows and the like.

### Reading members of forms and documents

A form's fields shadow its members, so `<input name="parentNode">` makes `form.parentNode` the input, and a named image does the same to its document. So members of a node that can be a form or a document (anything typed as `Node`, `ChildNode`, `ParentNode`, `Element` or `Document`) are read through the helpers at the end of `src/morphlex.ts`, like `parentNodeOf(node)` and `getAttribute(element, name)`, which call the member on the prototype that defines it. An element narrowed to an input, an option, a select and the like, or a text node, is read directly.

### Shadow roots as the inner morph root

`morphInner` takes a shadow root as `from`. It has no tag to match, so its target is the content itself: a `DocumentFragment` or another shadow root, whose children it takes, or a string parsed with its host as the context and without trimming its edge whitespace, as `shadowRoot.innerHTML` would. An element target throws, and the overloads make it a type error too. Its children are flagged and matched like an element's through `#morphChildNodes`, without what's special to templates, selects and textareas. Nothing around it counts, since forms and selects don't reach across the shadow boundary.
